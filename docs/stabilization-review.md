# PR #1 stabilisation review — 22 October 2026

Scope: correct existing branch `feature/platform-development-baseline`, preserve draft PR #1, no merge/deployment or new application features. This report supersedes the initial baseline's test/advisory totals; the application remains incomplete and development-only.

## Original CI failure and fixture correction

Run 39791703003 failed at the typecheck/lint/unit step; subsequent steps were skipped. Its run/job metadata was read (the archived log-download endpoint was initially blocked). The two supplied TypeScript failures were caused by passing `evt_success` to a helper whose default `crypto.randomUUID()` argument infers the UUID template type. Both calls now use a named deterministic valid UUID, checked with `satisfies ReturnType<typeof crypto.randomUUID>`. The helper type, compiler options and CI gates were not weakened.

The malformed unused `allowBuilds` strings generated by a different pnpm version were removed; pnpm 10's explicit `onlyBuiltDependencies` allowlist remains intact. Browser checks now have dedicated ports/API origin and a `.next-browser` directory, avoiding contamination from existing development servers or production builds.

## Financial and authentication fixes

- Payment webhook reconciliation now verifies the order metadata and service-fee allocation as well as connected account, currency and amounts. Concurrent duplicate receipts commit effects once; invalid events roll back their receipt so a corrected event is not lost.
- Known PaymentIntents are retrieved using the original payment account. Unbound creation attempts older than 23 hours fail closed because provider idempotency keys can expire after 24 hours. A later client retry cannot silently create a second charge. Intent response details are validated before returning its client secret.
- Refund requests attach the reserved key as Stripe metadata. Verified matching webhooks recover success even if the HTTP response/provider ID was lost. Account, payment intent, currency and exact refund amount must reconcile. Receipt, credit, audit and payment-state updates are atomic.
- Refund paths use consistent order→refund locking. Stale pending/failed responses cannot downgrade settled records; failed keys are terminal, pending reservations exclude new competing amounts and full-success retries do not double credit. Order and payment records remain consistent under late payment events.
- Partner-fee reversals use cumulative integer rounding. Configured tax snapshots correct a discovered 21p-versus-20p partial-refund VAT drift, and invoices preserve the resulting exact reversal. Historical ledger entries and old invoice totals are not rewritten. Tests use an explicit illustrative rate, not a UK VAT assumption.
- Cash completion still accrues exactly the customer service fee plus partner fee (£2 at launch fixture values); card completion invoices only the partner fee. Rejected/incomplete/cancelled orders accrue no completion fee. Existing regression assertions remain enabled.
- Checkout replay is bound to the authenticated customer as well as payload/tracking capability. Stale membership rows cannot grant a customer partner privileges. Role/disabled changes revoke sessions; verification holds the user access row lock until session creation. Upgrade migration 0007 signs out existing sessions once. OTP expiry/lockout, logout/session expiry and administrator MFA replay are tested.

## Provider documentation verification

The official [direct charges](https://docs.stripe.com/connect/direct-charges) and [direct-charge fee behaviour](https://docs.stripe.com/connect/direct-charges-fee-payer-behavior) documentation was fetched and read. It confirms the selected connected-account context and `fees.payer=account` allocation: the application fee contains only the platform service fee, and Stripe processing fees are separately deducted from the connected account. Disputed amounts debit that account first; ultimate negative-balance liability depends on controller configuration. Refunds do not return application fees automatically; the explicit adapter flag is required. These findings support the existing fail-closed Standard/controller checks, not all possible Connect models. Real connected-account, payout, dispute and provider-refund tests remain unverified without test credentials and contractual/country review.
