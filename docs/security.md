# Security review — payment isolation follow-up, 22 October 2026

No merge, deployment, production payment or external provider verification is authorised or performed. The backend image now supports `NODE_ENV=production` HTTP semantics, **not production-payment activation or a readiness certification**. Startup requires secure cookies, HTTPS public/mail configuration, an MFA encryption key and a restricted database login. All Stripe adapters still reject live keys; signed live webhook events are rejected.

## Implemented and tested

- Five-minute, hashed, single-use email challenges, five verification attempts and database row locks. Atomic PostgreSQL abuse buckets apply to source IP, normalised email and challenge ID across API processes; DB errors fail closed. Existing in-memory request limits remain an additional layer. Behind a proxy, configure only its explicit `TRUST_PROXY_CIDRS`; trusting arbitrary forwarded IP headers is prohibited. Worker removes expired abuse buckets after a day.
- Random opaque hashed sessions expire after twelve hours; every successful login issues new session/CSRF values. HttpOnly/SameSite Strict cookies become Secure automatically in production semantics. API responses use `Cache-Control: no-store`. Logout, other-session revocation, MFA rotation/recovery and access-change triggers revoke credentials appropriately. Role and disabled status are checked on every request; login share-locks the user row against concurrent access changes.
- Administrator TOTP credentials are individual encrypted database rows. AES-256-GCM uses a separate 32-byte `MFA_ENCRYPTION_KEY` and user-ID authenticated data. Ciphertext tampering and moving ciphertext between users fail authentication. No shared `ADMIN_MFA_SECRET` fallback remains. Initial enrollment requires an operator CLI; authenticated rotation requires a fresh current TOTP, session-bound expiring enrollment and confirmation of a new TOTP. Rotation revokes every session and supplies ten random single-use hashed recovery codes. Recovery also requires a valid email OTP and revokes old sessions. TOTP counters cannot be replayed. Secrets/recovery codes are returned only for explicit enrollment/rotation and must be stored privately.
- Parameterised SQL, input/body limits, current role/membership checks, authenticated-write CSRF checks and owner-only finance/payment management. Additional negative tests cover connected-account access across tenants. Ledger, pricing, audit, invoice lines and financial snapshots retain their existing immutable constraints.
- `infrastructure/database/runtime-role.sql` provisions the NOLOGIN `north_runtime` group. Its separately managed login receives only named data tables, required sequence use, and append-only financial/audit grants. It cannot migrate, create schema objects, truncate or mutate immutable records. Production-semantics API/worker startup rejects privileged/owner-like connections. Tests exercise actual `SET LOCAL ROLE` permissions and a container uses a temporary restricted login. Tenant isolation is enforced by application predicates; **database RLS is not implemented**.
- Fastify Helmet, restricted development CORS (production API disables cross-origin browser access), same-origin portal proxies, generic errors and sensitive-header redaction. Next now uses dynamic, uncacheable HTML with fresh script nonces and strict-dynamic CSP, constrained Stripe frame/connect origins, anti-framing/no-sniff/referrer/permissions headers and HSTS under secure configuration. Dev-only unsafe-eval is excluded from production; the read-only web image smoke checks fresh nonces. The prepared Caddy configuration supplies strict static portal headers and HTTPS routing, and blocks private metrics. It has not been deployed.

## Reconciliation/staging hardening follow-up

Administrator grants now have four explicit scopes (operations, finance, support, governance). New administrators default to no platform grants; legacy administrators are backfilled on upgrade and signed out once. Role-incompatible grants are rejected by PostgreSQL and cleared on demotion. Permission/membership changes revoke sessions. Access changes require fresh TOTP/reason, audit the exact role/grants/memberships and cannot remove the last enabled, individually enrolled access governor. The legacy staff route cannot reassign an administrator and now requires governance scope. No impersonation endpoint exists.

Additional DB protections enforce order/ledger partner consistency, cross-tenant order item and invoice-line rejection and immutable product tenant identity. Provider events, balances, payout links and financial adjustments are append-only; financial fields of mutable dispute/payout/application-fee projections are guarded separately. Guard-function search paths put pg_temp explicitly last, with a regression against temporary-table shadowing. These are tested defence-in-depth controls, not complete database RLS.

MFA keyrings support named AES-GCM keys while retaining a legacy decryption key during migration. The operator rotation script re-encrypts transactionally, clears pending MFA enrollment rotations, revokes administrator sessions and audits IDs/counts without secrets. Malformed keyring errors do not reveal key values. Stripe signing-key rotation accepts a configured previous key only until an explicit expiry (production configuration limits overlap to 24 hours). Live secret/publishable keys remain refused. Production origins, URL protocols and trusted-proxy ranges are validated and cross-site mutation origins are rejected.

API readiness now verifies PostgreSQL and Redis; private bearer-protected metrics expose dependency/worker and queue health. No monitor token means no metrics access. Tests cover unavailable Redis, monitoring authentication and production origin rejection. The prepared proxy refuses public `/internal/*`. The isolated migrator uses the owner credential separately; API/worker never receive it. The standalone web image explicitly prunes Next's optional global TypeScript build compiler after successful compilation and retains a strict runtime package check. No audit suppression or reduction in build-time type checks is involved.

Local encrypted-MFA rotation and guarded backup/restore tests passed with synthetic data; no hosted secrets, TLS, provider delivery or production recovery was verified.
