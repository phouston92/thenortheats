# VPS staging preparation — NOT deployed

This is a reviewable configuration and recovery procedure. No VPS was contacted, no Compose staging stack was started and no live payment configuration is present. A separate deployment instruction and review are required before executing the release/cutover steps below. Local test containers and disposable restore databases do not constitute a staging deployment.

## Configuration and release artifacts

`infrastructure/staging/compose.yaml` defines an API, worker, Next website, static partner/admin portals, Caddy, PostgreSQL 17.7, Redis 7.4.7 and private Prometheus. Keep each environment's project name, volumes, secrets, hostnames and network independent. Check the example 172.30.92.0/24 subnet for conflicts before selecting it; the fixed edge address is the only trusted forwarding proxy. The private bridge is not `internal` because Stripe/mail require outbound HTTPS. Database, Redis, API and monitoring have **no published host ports**; only the edge publishes 80/443. Apply a host firewall and SSH key access with a separate operator account.

Application image builds (local/release CI only):

```bash
docker build -f infrastructure/docker/backend.Dockerfile -t north-backend:review .
docker build --target migration -f infrastructure/docker/backend.Dockerfile -t north-migrator:review .
docker build -f infrastructure/docker/web.Dockerfile -t north-web:review .
```

Backend final runtime and separate one-off migrator contain compiled JavaScript and the pruned backend runtime dependency tree; mobile manifests are absent even during their dependency installation. Only the migrator contains migration SQL/entry point. The Next standalone image excludes route compiler traces and explicitly removes Next’s optional global TypeScript compiler after successful build/type checks and carries no Expo/mobile/test/compiler dependency packages. CI checks both application images, runs the backend with a restricted login and the web image non-root/read-only, and verifies fresh per-response script nonces. These checks do not replace OS-image scanning, signature/provenance review or vulnerability remediation.

Pin `BACKEND_IMAGE` and `WEB_IMAGE` to reviewed registry **digests**, not mutable tags, before deployment. The example infrastructure tags are version pins for reproducibility, not a claim that an OS scan has passed; scan and pin their digests too. No image was published to a registry in this task. Build static Vite artifacts in CI and supply the immutable reviewed directory through `PORTAL_ARTIFACTS`, containing `partner/` and `admin/`. The Next image is built with internal `API_ORIGIN=http://api:3001`; changing that topology requires a rebuilt image. Static portals and Next use their same-origin `/api` edge route.

## Private configuration

Use a secret manager to materialise a directory outside the checkout. `SECRETS_DIR` is not a Git directory and must not enter the Docker build context. Store each secret as its own private file. API/worker/Redis/monitor run with UID/GID 1000 in the template; prepare their owned volumes and required mounted files for that UID. With local Docker Compose, file-backed `secrets` bind mounts can retain host ownership/mode despite Compose uid/mode settings. Verify actual container readability and deny other host users. Do not make secrets world-readable to work around ownership. PostgreSQL uses its own image's data ownership/entrypoint rules.

Required files:

- `migration_password`: a random schema-owner password, mounted **only** into PostgreSQL initialization. Provision a separate migration URL for the isolated one-off migrator; never mount it into API/worker.
- `runtime_database_url`: the distinct backend login URL. After migrations apply `infrastructure/database/runtime-role.sql` and grant its NOLOGIN group to the separately provisioned login. Backend startup refuses schema-owner/superuser/create-role/create-db/replication/bypass-RLS or immutable-ledger mutation powers. Use authenticated private networking/TLS appropriate to the selected database service.
- `redis_config`: private Redis configuration with `dir /data`, `appendonly yes`, `appendfsync everysec`, protected mode, default user disabled, a strong runtime ACL and a separate health ACL. Runtime needs BullMQ commands/scripts on `bull:north-outbox:*` plus `north:worker:*`; health needs PING only. Generate password hashes/ACL lines privately, never in committed examples. `redis_url` contains the runtime ACL credentials; `redis_health_password` is the separate health account credential.
- `mfa_keys`: JSON mapping named key IDs to independently generated 32-byte hex keys; `mfa_active_key` selects the active ID. Keep these keys out of database backups. Existing legacy MFA ciphertext requires the legacy key during a controlled rotation (see below).
- `mail_webhook_url`: an approved HTTPS delivery service; development spooling is prohibited by production settings. Provider credentials/integrity requirements must be reviewed independently.
- `monitoring_token`: at least 32 random characters. Only API/worker and the private monitoring service mount it. Do not expose `/internal/metrics` publicly.

Set `PUBLIC_ORIGIN`, `PARTNER_PORTAL_ORIGIN`, `ADMIN_PORTAL_ORIGIN` to their exact HTTPS origins and supply corresponding `CUSTOMER_HOST`, `PARTNER_HOST`, `ADMIN_HOST`. Caddy requires working DNS and reachable 80/443 for automatic certificate management; its certificate/config volumes persist across replacement. The backend only trusts the explicit Caddy address. Caddy overwrites forwarding headers; direct API access stays private. Host-only Secure/HttpOnly/SameSite Strict sessions and CSRF checks remain enabled. Cross-site mutation origins are refused.

**Stripe is absent from the staging Compose environment/secrets by default.** Do not add `sk_live_`/`pk_live_` values. A separately reviewed test-only overlay can mount test settings through the whitelisted `*_FILE` loader after the provider procedure is authorised. All adapters continue to reject live keys/events. This task created no such active overlay and performed no provider operation.

Validate the file with `docker compose -f infrastructure/staging/compose.yaml config --quiet` after supplying the reviewed image/hostname/path settings. Validation does not start containers and does not validate secret contents, host ownership, DNS, TLS, provider contracts or backup restoration on the VPS.

## Persistence, backup and restore

Named volumes hold PostgreSQL data, Redis AOF, Caddy state and monitoring history. Never use `docker compose down -v` for a release or rollback. Redis is coordination/queue storage; financial truth and reconciliation evidence are in PostgreSQL. Agree RPO/RTO and retention with the business; no arbitrary compliance promises are invented here.

Use matching PostgreSQL 17 client tools and a separately scoped backup account. Keep `PGSERVICEFILE` and `PGPASSFILE` in private storage (mode 0600); `PGSERVICE` selects the intended connection. Avoid passwords in command arguments. `scripts/operations/backup.sh /private/backups/north-YYYYMMDD.dump` creates a mode-0600 custom-format backup, checks its table of contents and writes a SHA-256 manifest without overwriting an existing destination. The backup includes encrypted MFA records, audit/ledger data and sensitive user data. Encrypt it with the approved off-host recipient/KMS workflow before transfer, verify the encrypted copy and maintain an independent retention policy. Back up MFA keys separately under stronger access controls; a database backup without its valid key version cannot recover administrator authentication.

Restore to a newly provisioned, empty isolated database named `…_restore_YYYYMMDD` or `…_restore_test`, never over an active database. Privately select its service connection and set `RESTORE_CONFIRMATION=restore-into-empty-database`, then run `scripts/operations/restore.sh verified-backup.dump`. The script checks SHA-256, refuses a nonempty/unapproved target name and uses a single transaction with exit-on-error and no owner/ACL restoration. Reapply runtime grants and separately provision logins. Validate migration checksums, data counts and immutable ledger/reference/tax totals; reconcile provider events after the backup point before any cutover. Keep provider processing paused during a separately authorised recovery to avoid old-worker/double-write races.

`pnpm test:restore` has actually exercised a PostgreSQL 17 dump and restore locally into a fresh disposable `_test` database, comparing migration checksums, financial counts and the immutable ledger digest. It removes only its own temporary database/dump. This is **not** a VPS/PITR/HA recovery drill. WAL archiving/PITR, encrypted off-site recovery, key availability and agreed RPO/RTO still need a hosted operational test. Redis AOF restore/queue replay must be tested separately; never treat Redis recovery as a substitute for financial reconciliation.

## Release procedure — instructions only

1. Obtain separate staging deployment approval; review exact source/image digests, unresolved audit findings, OS scans and external provider/security blockers. Confirm database backups and migration compatibility. Do not treat this task as that approval.
2. Put order/payment writes into the agreed maintenance state and drain workers. Record financial high-water marks, outstanding jobs and a verified backup. Provision private secrets, DNS/TLS prerequisites, owned volumes and the runtime login. Existing database volumes do not rerun `POSTGRES_PASSWORD_FILE` initialization; rotate existing credentials explicitly.
3. Run the separately built migrator image as a one-off job with **only** the schema-owner database URL, supplied through a private `DATABASE_URL_FILE`. It applies checksum/advisory-locked migrations atomically. Run twice to confirm idempotency; apply the updated runtime-role grants after migration. Never grant API/worker the migration credential. Migrations 0010–0014 add evidence/projections/permissions/tenant guards without rewriting historical financial rows; upgrade revokes legacy administrator sessions once. Review/backfill anomalies cause migration failure rather than silent deletion.
4. Enroll initial administrators individually, grant reviewed scopes and test governance/finance separation. Stage both MFA key versions before rotation, run `pnpm admin:rotate-key` only as an authorised operator in an isolated trusted environment, verify all rows moved to the named active key, then retire the old key. Rotation is transactional, clears pending authenticator rotations, revokes administrator sessions and audits key ID/count without plaintext. Keep the old key available until every instance/backup retention requirement is addressed.
5. Only under that separate approval start/replace the prepared services, wait for PostgreSQL/Redis/API readiness and the worker heartbeat, and validate edge routing/cookies/CSP/no public data ports. Run read-only smoke checks, authenticated admin health and a synthetic cash flow before enabling test-mode provider exercises. Live payments remain disabled.
6. Follow `stripe-test-procedure.md` for explicitly authorised real test-mode operations. Save actual evidence and resolve provider exceptions; no real customer traffic is approved by this runbook.

## Monitoring and rollback

`/api/health` is liveness. `/api/ready` checks PostgreSQL and Redis and returns 503 on unavailable dependencies. Worker heartbeat lives in Redis with a 30-second TTL, namespaced by `NORTH_INSTANCE`. Administrator operations health reports dependencies and queue counts. `/internal/metrics` requires a separate bearer secret and exposes no user/card/credential data; Caddy blocks that path. Prometheus/alert rules cover API/dependency/worker loss and pending/blocked reconciliation/compensation. The alert receiver, escalation owner, off-host logging/availability probes and delivery tests are **not configured** by this preparation. Prometheus alone is not an incident response system.

If application checks fail, leave writes paused, stop/drain the new worker and switch to the previous reviewed application digest only if it supports the current forward schema. Do not reverse/drop immutable finance migrations or replace a live volume. If rollback is schema-incompatible, restore the verified backup into a **new** database, validate it, reconcile all Stripe activity since the backup point and obtain explicit cutover approval. Record the old/new database identity and ensure only one worker/API writer set can reach the active financial database. Preserve old volumes/evidence for investigation. Re-run readiness, security, financial and provider checks before reopening writes.

Staging remains blocked by missing real Stripe evidence, unpatched mobile-toolchain advisories, image/OS security approval, hosted backup/key recovery and TLS/monitoring/secret-manager validation. Local preparation is not deployment readiness certification.

Rollback compatibility includes **authorisation and encryption semantics**, not only SQL shape. Images predating the four administrator scopes would treat a finance-only administrator as fully privileged, and images predating named MFA keyrings cannot decrypt the new ciphertext. Do not roll back to those images while scoped administrator accounts/named-key records are active. Use a compatible reviewed application build, or a separately approved recovery that preserves access restrictions and provider evidence. Old webhook/compensation code also lacks the new Dashboard/dispute safeguards. Keep writers paused until compatibility and all external event backlog are reconciled.
