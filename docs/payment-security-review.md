## Financial checks

The agreed configured launch policy remains £1 customer service fee and £1 completed-order partner fee. Completed cash orders accrue £2 exactly once; completed card orders accrue only the partner fee in invoicing because the customer fee belongs to the direct-charge application fee. Cancellation before completion accrues neither completed-order fee. Existing concurrency, duplicate webhook/completion/refund, signed account/currency/amount/allocation checks, cumulative partial fee/VAT reversals, legacy VAT snapshots, immutable records and invoice idempotency are retained.

New tests exercise repeated intent resume; failed/ambiguous capture with a stable key and no fulfilment advancement; rejected captured-order refunds after a lost provider response; concurrent compensation attempts; terminal refund failures with no financial credit; late signed capture after cancellation; MFA ciphertext tampering/cross-user substitution, rotation/recovery replay and session invalidation; shared abuse counters across API instances/source IPs; Connect tenant permissions; runtime-role DDL/immutable mutation denial. These are local provider-double/SDK-spy tests, not provider execution.

## Blockers before expanding the application

1. Supply private **test-only** Stripe keys/webhook secret and a supported Standard test account. Verify onboarding, actual controller/processing-fee ownership, £1 application-fee allocation, card/3DS checkout, duplicate/delayed external events, capture/refund failure behaviour and payouts. No live activation is permitted. Agree the country/contract and tax/refund policy with Stripe/accountant.
2. Resolve or explicitly manage upstream mobile advisories through a reviewed security decision; the required audit currently prevents green CI. No exception has been introduced.
3. Implement provider-side settlement/dispute/external Dashboard refund reconciliation and an operational process for blocked/aged ambiguous operations. Cash refund endpoints remain intentionally unavailable without confirmed repayment. Worker/provider configuration is necessary for automatic compensation; an unconfigured provider does not mean money was returned.
4. Complete RLS/composite tenant keys, granular roles/admin access governance, secret-manager/key-rotation and lost-factor incident drills, strict script CSP/static portal deployment headers/TLS, idle timeout/retention/privacy controls and independent security review.
5. Exercise backup restore/failover/monitoring, migration release procedures and OS-image scanning before any separately authorised staging task. Existing incomplete scheduling, modifiers, invoice issuance/credit-note workflow, notifications and native payment features remain outside this stabilisation task.

Ready for focused provider verification and security remediation; **not ready for broad feature expansion or deployment** until these blockers are resolved. Draft PR remains open and unmerged.
