# Stripe test-mode verification procedure

As of 22 October 2026 no private Stripe secret key, publishable key, webhook signing secret or connected test-account ID was available in the task process or private local configuration. **No real Stripe provider requests, payments, onboarding, 3DS, refunds, disputes or payouts were executed.** `pnpm stripe:verify` reports missing field names and exits 2; it never manufactures a provider result or performs a write.

## Private prerequisites

Use an authorised Stripe **test-mode** platform with Connect enabled for the intended UK configuration, a Standard test connected account (or an authorised test account to onboard), a private `sk_test_…` API key, matching `pk_test_…` key, and Connect/platform endpoint signing secrets. Store them in the environment's secret store or private mode-0600 runtime files; never Git, PR comments, screenshots, logs or chat. Configure `STRIPE_TEST_ACCOUNT_ID` for the read-only verifier. Production keys and live objects/events are rejected in code. A payout/bank fixture must be a Stripe test bank configuration, not a real bank/customer.

Grant the developer/operator access to that platform and connected account in Stripe's dashboard. Confirm test operations are within the supported account's country/capabilities and intended fee/loss contract. Configure external mail separately for identity verification. Use only synthetic customer identities and test card numbers. Real transactions remain unauthorised.

## Read-only architecture checks

1. Export the private test settings and run `pnpm stripe:verify`. It retrieves account readiness only; success must show Standard, charges and payouts enabled, `controller.fees.payer=account`, `controller.losses.payments=stripe`. Save a redacted evidence record with date, platform/account aliases and actual results. Missing/unsupported/read failures are blockers, not passes.
2. The platform creates PaymentIntents **in the connected account** (`Stripe-Account` context), GBP, card only, automatic capture, `application_fee_amount=100` under the agreed launch policy. No destination transfer is used. The £1 completed-order partner fee remains in the platform invoice ledger. Verify the amount, metadata order ID and immutable payment account before exposing the client secret.
3. In the connected account, inspect charge/balance transaction fee details. Distinguish Stripe processing fees from the application fee: total balance-transaction `fee` may include both. Confirm the partner pays processing fees for this controller configuration. Verify net = gross − total fee, actual application fee £1 and that food/delivery revenue stays with the partner. Do not infer fee or loss liability from a mocked account object.

Reference documentation: [direct charges](https://docs.stripe.com/connect/direct-charges), [fee-payer behaviour](https://docs.stripe.com/connect/direct-charges-fee-payer-behavior), [test cards](https://docs.stripe.com/testing), [disputes](https://docs.stripe.com/disputes/testing), [payout reconciliation](https://docs.stripe.com/payouts/reconciliation), [webhooks](https://docs.stripe.com/webhooks). The adapter enforces the chosen configuration; real account/contract/processing/refund/dispute-fee evidence is still required.

## Webhook delivery and disorder

For local tests use an authenticated Stripe CLI in test mode. Check the installed CLI help, then forward Connect events using `stripe listen --forward-connect-to http://127.0.0.1:3001/api/webhooks/stripe --forward-to http://127.0.0.1:3001/api/webhooks/stripe`. Privately configure the emitted signing secret as STRIPE_WEBHOOK_SECRET. For hosted testing, separately authorised HTTPS endpoints and actual platform/Connect signing secrets are required. Configure STRIPE_WEBHOOK_SECRET for connected-account delivery and STRIPE_PLATFORM_WEBHOOK_SECRET for a distinct platform endpoint (application-fee events). Both can target this handler; a platform fee event may omit the top-level account, so its object.account is validated against the known connected account. Do not misuse the expiring previous-key slot as a permanent second endpoint secret. No VPS or public endpoint was created here. The bounded previous-secret overlap supports endpoint rotation, not unlimited acceptance of old secrets.

Subscribe to PaymentIntent succeeded/failed/capturable/canceled; refund created/updated/failed; charge succeeded/updated/refunded; application fee created/refunded; dispute created/updated/closed/funds events; payout created/updated/paid/failed/canceled. Balance transactions have **no fabricated webhook event** here: their `balance_transaction.snapshot` records come only from authenticated Stripe reads.

Resend a real event from Stripe's test dashboard/CLI, then resend relevant events out of order. Verify provider delivery attempts/signatures in Stripe as well as local receipts. Test refund-before-capture, close-before-dispute-create, late payment failure after capture, late capture after cancellation, old payout pending after paid and same-second contradictory payout statuses. Duplicate financial references must not multiply. Unmatched events must be visible and replayable; a conflicting projection requires fresh matching provider evidence before acknowledgement. Never send an invented signature to a real endpoint and call it successful provider delivery.
